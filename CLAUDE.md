# CLAUDE.md

Project context and build plan for a tender-response application. Read this file fully before writing any code. It records the decisions made during planning; where a decision is marked as an assumption, check with Puru before building on it. Revised on 28 September 2026 after a review of this plan against the Ten(der) pitch deck and a second review of the revision itself, and again on 30 September 2026 after Puru reviewed the front-end pull request (commit ba3e874) and accepted its scope additions as the product direction; the decision log at the end records what changed and why.

## What this project is

A web application that helps organisations respond to public procurement tenders. The company uploads its past tender submissions and its current compliance and reference documents. When a new tender arrives, the company uploads the buyer's documents, and the application extracts every question, triages which questions are already answerable from existing material, drafts answers with provenance, and tracks every question through human review to submission.

The first customers are health technology suppliers bidding to the NHS, because that is the founders' own domain and the corpus they can model. Care providers, hospices and other sectors follow. Nothing sector-specific may be hard-coded outside the three places designed to hold it: the editable topic taxonomy, the fixed lists in configuration (fact kinds, document kinds, lexical stopwords), and the demo data.

This is a hackathon MVP that is intended to become a SaaS product. The hackathon output is the first version of the product, which the funded round then hardens; it is not a throwaway. Puru owns the backend and the pipeline. Roger owns the visual design, the front-end implementation and the Next.js sidecar that holds identity and membership. This file specifies the backend, the pipelines, the information architecture the front end must present and the boundary between the API and the sidecar; it does not specify visual design.

## The core thesis

The chat is not the product. A general-purpose assistant can already take four PDFs and draft an answer to a pasted question. What it cannot do is know that this tender has forty-three questions, that eleven are already fully answerable from approved past material, that question 4.2 carries fifteen per cent of the score and nobody owns it, that the DCB0129 answer cites a superseded clinical safety case, and that the deadline is Thursday. The product is the tender as a tracked object. Chat is one tool inside it.

Every design decision should be tested against that thesis. A feature that a general assistant already offers is not a differentiator. The differentiators are: structured extraction of the question pack into tracked cards; coverage triage across the whole tender at upload time; per-question drafting with sentence-level traceability to source material, a gap list and a fact checklist; fact-level freshness against current reference documents; a review pipeline with an audit trail; export in the buyer's structure; and a learning loop that promotes approved answers back into the knowledge base.

The primary path is one question at a time. A user opens a question, receives a drafted answer in which every sentence points at the paragraph it came from, checks only the sentences that need checking, edits, and signs off. Whole-pack triage and draft-all are accelerators layered on that path. They reuse it and must never become prerequisites for it.

Traceability is a first-class requirement, not a display detail. Every sentence of every generated response must be traceable to the source material it was drawn from, and checking that trace must take one hover or one click, never a search. The trace must reach the uploaded document itself, not only the library's copy of it: a reviewer who clicks a sentence must land on the right paragraph of the right file with the supporting words highlighted. The purpose is to let reviewers verify only what needs verifying: a reviewer who has to re-read every source to trust a draft gains nothing over writing it themselves. See the section on traceability below; it constrains the ingestion pipeline, the synthesis output schema, the answer data model, the editor, and the export.

## What a solid MVP is

The MVP is done when one user can do the following, end to end, on the synthetic data, without a developer in the room:

1. Upload three past submissions and two reference documents, confirm the classification the system proposes for each, and see each document in the library reach `ready` with its counts of extracted question-answer pairs, chunks and facts; open one document's sections; and see the older of the two reference documents marked superseded once both are confirmed.
2. Create a tender, upload its question pack, and within about a minute see a board of question cards coloured by coverage.
3. Open a question and receive a streamed draft in which every sentence carries a marker; hover the marker to see the source excerpt; click it to open the original document at the paragraph, with the supporting words highlighted.
4. In the assistant thread, ask for the draft to be shortened and save the reply as the answer. Edit that version and see which sentences kept their sources and which became human-authored; open the version history and see the diff; attest to one sentence; dispute one supported sentence, then rewrite and attest to it; acknowledge one gap; set a compliance class; attach one evidence document; add a comment; assign the question to a named person; move it through the review states to approved, with every step in the event log.
5. In the table view, filter to the questions not yet approved; read the approved answers through in the document view in the buyer's order; export them as a docx in that order.
6. Open the latest evaluation report the harness produced from the same synthetic data.

Everything in the "must ship" list below serves one of those six steps, either on the step's path or as the fallback that keeps it truthful (the unpaired queue and pending supersession decisions for step 1; the verbatim option inside step 3's drafting, shown only when the pack holds a near-identical question). If a feature does neither, it is not MVP.

- Internal review export (docx with sources as Word comments) and xlsx export.
- Promotion of approved answers into the library on submission.
- Library screens beyond the document list, its sections view, the unpaired queue and pending supersession decisions: knowledge items with variants grouped under their canonical, facts with their supersession chain.

Built in the frontend sidecar (accepted on 30 September 2026 as the funded-round direction; see the decision log):

- Invite-only authentication with Supabase Auth; no self-sign-up.
- Businesses (workspaces), each mapped one-to-one to a backend organisation, with roles, teams and invitations.
- Reviewers per question and a "My tasks" view, read live from the backend's assignees.
- Notifications for assignments, status changes, comments and `@Display Name` mentions made through the application.
- Anchored comments on a span of an answer version, with mentions, mirrored to the backend's comments endpoint.
- Buyer-form filling: approved answers written into the original docx or xlsx at locations a person has confirmed.

The boundary: the sidecar owns identity, membership, invitations, notifications and confirmed form locations, in its own Postgres schema. The backend remains the record for tenders, documents, questions, answers, threads, comments and events; the sidecar never stores tender content and refers to backend rows by UUID only. The primary path, one question at a time, is unchanged and remains the demo spine; nothing in the sidecar is a prerequisite for it beyond signing in.

Out of scope (design for them, do not build them):

- Billing.
- Multi-tenant isolation in the API beyond an `org_id` column on every table and the organisation the proxy names per request; membership is checked in the sidecar, never in the API.
- Email delivery of notifications, and integrations with Notion, SharePoint, Atamis or procurement portals.
- A second local model for query expansion. A cross-encoder reranker.
- Retrieval over a tender's own documents (specification, clarification log, contract terms). They are stored and their sections are viewable; they are not embedded, indexed or searched.
- Post-award features: a commitments register, renewal reminders, buyer feedback capture. The tender outcome field exists so these can be added later.
- Pricing. The pipeline never drafts a price. Pricing questions are extracted, tracked and exported, but their answer region is human-only.
- OCR of scanned PDFs.

## Vocabulary

Use these terms consistently in code, API and UI. The abbreviation "RAG" is ambiguous in this domain (retrieval-augmented generation versus red-amber-green readiness). In this codebase, "RAG" is never used as an identifier. Retrieval is called retrieval. Readiness colours are called coverage (for retrieval-derived readiness) and status (for review state). The word "triage" means coverage triage and nothing else; the supplier's A/B/C judgement is called compliance class.

- Organisation: the company using the product. Owns the library, tenders and threads.
- Library: the organisation's knowledge base, consisting of documents, sections, knowledge items and facts.
- Document: an uploaded file. Has a `doc_type` of `past_submission`, `reference` or `tender_document`, a `doc_kind` for reference documents, a `tender_doc_kind` for tender documents, an `effective_date`, and a `superseded_by` pointer.
- Section: one parsed unit of a document, persisted at parse time and never edited: a heading-delimited block of prose, or one row of a table or spreadsheet. Every knowledge item and every citation points at a section. Sections are the ground the trace stands on.
- Knowledge item: a retrievable unit. Either a question-answer pair extracted from a past submission, a chunk of a reference document, or an approved answer promoted from a completed tender.
- Canonical item: a knowledge item chosen to represent a cluster of near-duplicate items. Variants remain attached.
- Fact: a discrete, dated, expiring claim extracted from a document (certificate numbers, DSPT year and status, Cyber Essentials Plus expiry, ISO 27001 scope and date, named clinical safety officer, headcount, insurance limits). Has a source section, an effective date and an optional expiry. `fact_kind` is one of a fixed list in configuration. `fact_key` names the subject of the fact when more than one can legitimately be current at once (a legal entity, a site, a product, a cover type, an accreditation name); it is never a date, a status or a certificate number, which belong in `value`, `effective_date` and `expires_on`. Kinds with one current holder use a null key.
- Tender: a procurement the organisation is responding to. Has a buyer, a deadline, a status, an outcome once known, and one or more tender documents.
- Tender document: a buyer-issued file attached to one tender: the question pack, a specification, a clarification log, contract terms. Tender documents are parsed and viewable but never enter the organisation library and are not retrievable.
- Question: one question extracted from a question pack. Has section, number, text, word limit, weighting, `response_type`, `mandatory` flag, topics, and an optional human-set compliance class.
- Compliance class: the supplier's own judgement of a requirement: A (compliant now), B (compliant by a stated date), C (cannot comply). One C on a mandatory fails a bid. It is set by a person, never by retrieval, and is distinct from coverage.
- Answer: a versioned response to a question. Each version has an author (`ai` or a user), text and segments (each sentence with its sources and support status). The review status belongs to the question and describes its current version.
- Thread: a chat conversation, scoped to a question or to a tender. Messages store retrieved item identifiers and citations.
- Coverage: retrieval-derived readiness for a question: `covered`, `partial` or `new`; `unknown` from question extraction until the triage job has recorded a result.
- Status: review state of a question's current answer: `not_started`, `ai_draft`, `writer_edited`, `sme_verified`, `approved`.
- Job: a background unit of work with progress: one per document ingest, question extraction, tender triage or draft-all run.

## Architecture and stack

Backend is Python 3.12 with FastAPI. Persistence is Postgres 16 with the pgvector extension; no separate vector database. Full-text search uses Postgres `tsvector` for the lexical half of hybrid retrieval; no separate search service.

Background work runs in a separate `worker` process that consumes a `jobs` table in Postgres. Both processes are built from the same image and started by docker compose. The API process runs LLM calls only where a request is waiting on them: the two streaming endpoints, the re-verification that runs when a human edit is saved, and the support verification that runs when a verbatim offer is accepted; the last two run synchronously in the request and return in a few seconds. `POST /documents/{id}/pairs` also calls `embed()` for the one item it fixes. Everything else that takes more than a second is a job on the worker. FastAPI `BackgroundTasks` are not used. A Postgres-backed job loop is about a hundred lines and buys two things the demo needs: a document stuck mid-ingest survives an API restart, and Docling never runs inside the process that is streaming answers.

The hackathon runs exactly one worker. It takes queued jobs in `created_at` order and sets each to `running` with `attempts + 1`. On start-up, jobs left in `running` are requeued if `attempts` is below `max_attempts` (in `config.py`, default 3); otherwise they are set `failed` with `error` recording that the worker died during the job, a `job_failed` event is written and, for `ingest_document` and `extract_questions`, the document's `ingest_status` is set `failed`. A job whose run raises is handled the same way: below `max_attempts` it goes back to `queued` with the exception in `error` and is picked up on the next loop; otherwise it is `failed` as above. A requeue never resets `attempts`. Per-item failures inside `extract_questions` and `draft_all` are recorded in `results` and do not raise to the job. A requeued `ingest_document` resumes at the first step of the stage recorded in `ingest_status`; the stages are idempotent (ingestion step 9). `extract_questions` is idempotent on (`tender_id`, `section`, `number`): a re-run updates existing rows rather than inserting duplicates. When the queue is empty the worker also runs the fact-expiry sweep described under traceability, at most once an hour.

Single-question drafts and thread replies run in the API process as detached `asyncio` tasks (`asyncio.create_task`, held in a module-level registry keyed by question or thread id so they are neither garbage-collected nor duplicated). The task writes stream events to an in-memory queue and persists the answer or message when it finishes; the streaming response only drains the queue. A client disconnect closes the response and stops draining; the task keeps running and still persists. The task opens its own database session, never the request's, and in a `finally` closes it and removes its registry entry, so an exception never leaves a stale entry behind. The registry and queues are process-local, so the API runs as a single uvicorn process (`--workers 1` in compose). These are not `jobs` rows and return no `job_id`; the `done` event carries the persisted id. An in-flight draft does not survive an API restart; unlike ingest, that is accepted for the hackathon, and the user regenerates. Draft-all, if built, calls the same pipeline function from inside the worker with no queue or stream.

Document parsing uses Docling for docx, xlsx and PDF, preserving tables and section structure. The parsed sections are persisted (see data model). Docling's PDF layout and TableFormer weights are the one local model in the build: the Dockerfile downloads them at image build time and sets `DOCLING_ARTIFACTS_PATH`, the PDF pipeline is constructed with that path and `do_ocr=False`, so no weights are fetched at run time. docx and xlsx parsing uses no models. LLM calls use the Anthropic SDK with Claude for classification, extraction, topic labelling, query rewriting, coverage judgement, synthesis and entailment, or the heuristic double in synthetic demo mode (below). Embeddings use an external embedding API behind a single `embed(texts) -> vectors` function selected by environment variable (default `text-embedding-3-small`; Voyage is the alternative). The vector column dimension is read from configuration at migration time; changing to a provider with a different dimension is a re-embed of the library and of `questions.embedding`, which the harness must be able to run.

There is no reranker in the product retrieval path. The corpus for an early customer is a few hundred items, fusion of three ranked lists does the ranking, and the coverage judgement is an LLM call that already reads the candidates. The harness keeps an optional LLM rerank toggle, built in Phase 5 tuning as one schema-validated call over the fused candidates, so the question can be answered with numbers later. A local cross-encoder is not part of the build.

The front end is a separate Next.js application, owned by Roger, that consumes the REST API from its server only; the browser never calls the API. The Next.js server proxies an allow-listed set of routes, methods and query parameters (`frontend/src/server/backend/policy.ts`), injecting `X-Actor` (the member's display name, unique within the business, never `system`), `X-Org-Id` (the business's backend organisation) and a bearer service secret. A browser-supplied identity or authorisation header is refused with 400; a mutation must carry the application's own origin and `X-Ten-Request: 1` or is refused with 403. Uploads and NDJSON streams pass through the proxy as streams; only small question mutations and comment bodies are read, to validate assignees and emit notifications. The API is service-authenticated: when `SERVICE_SECRET` is set (at least 32 characters), every route including `/health` requires `Authorization: Bearer <secret>`, compared in constant time; there is no other authentication in the API. Beside the API the sidecar keeps its own Postgres schema (`app.*`, under `frontend/supabase/migrations/`) for profiles, workspaces, memberships, invitations, notifications, activity, reviewers, comment anchors and confirmed form locations, protected by row-level security; it holds no tender content. Draft generation streams to the client through the proxy (see the streaming contract under the API surface). `/health` reports the LLM and embedding providers, whether the secret is enforced and whether synthetic demo mode is on; the front end in demo mode refuses to boot against fake or synthetic providers or an unenforced secret.

Synthetic demo mode. `SYNTHETIC_DEMO=true` selects `app/llm/synthetic.py`, a deterministic rule-based double for the language model that knows the three synthetic layouts and the fact sentences the generator writes; it is not a model and extracts nothing useful from a real document. It requires `LLM_PROVIDER=fake` and `EMBEDDING_PROVIDER=fake`, or the API and the worker refuse to start. In it both upload routes, library and tender documents, accept only files whose SHA-256 matches one of the supplied `eval/data` files and return 422 for anything else, and the interface labels the mode. It exists so the joined stack runs end to end without keys. Its results are plumbing evidence only and are never quoted as benchmark numbers (see the evaluation harness).

The whole stack runs with a single `docker compose up --build` from the repository root: `db` (Postgres with pgvector, holding the backend and the sidecar databases), `migrate` (Alembic and the backend seed), `api`, `worker`, `config`, `auth` (GoTrue), `gateway`, `frontend-migrate`, `frontend-provision` (development accounts, businesses and their backend organisations), `frontend-seed` (the synthetic library documents and question pack; re-runnable, and `web` does not wait for it) and `web`. Only port 3000 is published; the API, the worker, auth and the databases stay on the Compose network. Uploads are capped at `MAX_UPLOAD_BYTES` (25 MiB by default) by the proxy and again by the API, which refuses an oversized body before spooling it. Nothing is downloaded at start-up. The local stack defaults to synthetic demo mode with fake providers and a local-only service secret; a live run uses the `docker-compose.live.yml` override, which sets `SYNTHETIC_DEMO=false`, `LLM_PROVIDER=anthropic` and a real embedding provider, with their keys and a random secret, three variables that change together. Native runs (uvicorn and the worker from `backend/`) read `.env` at the repository root and default to live providers through `.env.example`. The seed still creates the default organisation and the fixture document for the tests and the harness; the sidecar provisions every other organisation through `POST /organisations`.

## Data model

All tables carry `id` (UUID), `org_id`, `created_at`, `updated_at`. Vector columns use pgvector with the embedding dimension set from configuration. Offsets everywhere (`answer_start`, `question_start`, locator `start` and `end`, highlight ranges) are Unicode code-point indices into the raw stored section `text`; the front end converts to UTF-16 indices before highlighting.

- `organisations`: `name`, `topic_taxonomy` (JSON list of snake_case identifiers, seeded from the default taxonomy below; editable in future, but identifiers referenced by the fact-kind mapping in `config.py` may not be removed or renamed, and the seed asserts this). One row per business in the sidecar, provisioned through `POST /organisations` with the sidecar's id; the seed creates the default organisation for the tests and the harness.
- `documents`: `filename`, `storage_path`, `doc_type` (nullable until classification has run: `past_submission` | `reference` | `tender_document`; set at upload for tender documents), `doc_kind` (nullable; reference documents only, from the configured list: `dspt_confirmation`, `cyber_essentials_plus`, `iso_27001`, `clinical_safety_case`, `information_security_policy`, `product_description`, `other`), `tender_id` (nullable; tender documents only), `tender_doc_kind` (nullable: `question_pack` | `specification` | `clarification_log` | `contract_terms` | `other`), `effective_date`, `effective_date_source` (`extracted` | `upload_time` | `user`), `classification_confirmed` (boolean; false until the user confirms or overrides a library document's classification; set true at upload for tender documents, which are never classified, and by the seed for the fixture document), `superseded_by` (nullable document id), `buyer` (nullable, for past submissions), `submission_date` (nullable), `outcome` (nullable: `won` | `lost` | `unknown`), `ingest_status` (`queued` | `parsing` | `classifying` | `extracting` | `embedding` | `linking` | `ready` | `failed`), `ingest_error`.
- `document_sections`: `document_id`, `order_index`, `heading_path` (JSON list), `page_start`, `page_end` (null for spreadsheets), `table_index` (nullable; set for table-row sections), `cell_ref` (nullable; the row reference of a table-row section, such as `Sheet1!5` or `T2:R5`), `text`. Written once at parse time, never edited. Granularity: prose is one section per heading-delimited block, a heading line and the paragraphs beneath it up to the next heading of any level. Sections never overlap and every character of prose belongs to exactly one section; a sub-heading's paragraphs belong to the sub-heading's section, not its parent's, and `heading_path` carries the ancestry. The section's `text` begins with its own heading line, except for prose before the first heading, which is one section with an empty `heading_path`. Every docx table and every xlsx sheet is one section per row, with `heading_path` being the enclosing prose heading path followed by the header row's cell texts and `text` being the row's cells in column order joined by the cell delimiter in `config.py`.
- `knowledge_items`: `document_id`, `section_id` (the answer's section), `answer_start`, `answer_end` (offsets into that section's text), `question_section_id` (nullable; null means the same section as `section_id`), `question_start`, `question_end` (nullable), `item_type` (`qa_pair` | `chunk` | `promoted_answer`), `question_text` (nullable for chunks), `answer_text`, `text_verified` (boolean: the stored text was sliced from, or found in, the section), `topics` (text array), `canonical_id` (nullable; the cluster's canonical item, null on the canonical itself), `is_canonical`, `question_embedding` (vector, nullable), `answer_embedding` (vector), `search_tsv` (generated tsvector, see retrieval), `excluded_from_retrieval` (boolean; true when the source document is superseded). Retrieval eligibility is `excluded_from_retrieval = false and text_verified = true`; wherever this file says "eligible items" it means both.
- `unpaired_fragments`: `document_id`, `section_id`, `role` (`question` | `answer` | `unknown`), `text` (the model's copied text), `start`, `end` (nullable offsets; set when the anchor was located), `resolved_item_id` (nullable knowledge item id; set when a person pairs it). Holds genuinely unpaired fragments only. A pair whose fidelity check failed is not a fragment: it is a `knowledge_items` row with `text_verified = false`.
- `facts`: `document_id`, `section_id`, `knowledge_item_id` (nullable), `fact_kind` (from the configured list), `fact_key` (nullable), `statement`, `value`, `effective_date`, `expires_on` (nullable), `expired_at` (nullable; set by the expiry sweep), `superseded_by` (nullable fact id).
- `supersession_decisions`: `doc_kind`, `document_a_id`, `document_b_id` (unique on the unordered pair), `reason` (`auto` | `pending_date` | `tie` | `keyed_kind`), `decision` (`pending` | `superseded` | `keep_both`), `superseding_document_id` (nullable), `decided_by` (nullable; null means automatic), `decided_at` (nullable). One row per pair of confirmed reference documents of a supersedable kind.
- `tenders`: `name`, `buyer`, `deadline`, `status` (`open` | `submitted` | `archived`), `outcome` (`pending` | `won` | `lost` | `unknown`), `outcome_notes` (nullable), `regime` (nullable: `procurement_act` | `psr` | `pcr_2015` | `other`), `is_framework` (nullable boolean), `submitted_at`, `extract_job_id` (nullable), `triage_job_id` (nullable), both holding the latest run.
- `questions`: `tender_id`, `document_id` (the `question_pack` it was extracted from), `section`, `number`, `text`, `word_limit` (nullable), `weighting` (nullable), `response_type` (`free_text` | `yes_no` | `attachment` | `table` | `pricing` | `other`), `mandatory` (boolean), `order_index`, `topics` (text array), `embedding` (vector; the question text embedded once at extraction), `coverage` (`covered` | `partial` | `new` | `unknown`), `coverage_detail` (JSON: `best_vec`, `label_source` (`floor` | `llm`), top candidate ids and scores, gap summary), `compliance_class` (nullable: `A` | `B` | `C`), `compliant_by` (nullable date), `assignee` (nullable display name), `status`, `needs_review` (boolean), `gap_acknowledgements` (JSON list of `{gap, acknowledged_by, note, at}`).
- `question_evidence`: `question_id`, `document_id`, `note`. The attachments and evidence the answer will point the buyer to; distinct from citations.
- `answers`: `question_id`, `version`, `author_type` (`ai` | `user`), `author_name` (null for AI versions), `text`, `word_count`, `segments` (JSON list, see traceability section; the canonical record of what each sentence rests on), `gaps` (JSON list of strings), `fact_checklist` (JSON list of `{fact_id, statement, effective_date, status}`; `status` is `current`, `superseded`, `expired` or `unverified`), `verbatim_offer_item_id` (nullable; the item offered as a verbatim alternative alongside this version), `verbatim_source_item_id` (nullable; this version is the verbatim copy of that item), `support_summary` (JSON: counts of segments by `support_status` and the derived support score), `model`, `prompt_version` (both null on verbatim and human versions), `is_current`.
- `threads`: `tender_id`, `question_id` (nullable; null means tender-level thread; unique where not null), `title`. One thread per question, created together with the question row at extraction.
- `messages`: `thread_id`, `role` (`user` | `assistant` | `system`), `content`, `segments` (JSON, same shape as on answers), `rewritten_query`, `retrieved_item_ids` (JSON), `support_summary` (JSON), `gaps` (JSON), `fact_checklist` (JSON), `verbatim_offer_item_id` (nullable), `model`, `prompt_version` (the values that produced an assistant message), `answer_id` (nullable; set when the message was saved as an answer). All assistant-only fields are null on user messages.
- `events`: `entity_type`, `entity_id`, `event_type` (`status_changed` | `assigned` | `answer_created` | `answer_saved_from_chat` | `verbatim_accepted` | `comment_added` | `document_superseded` | `supersession_decided` | `pair_fixed` | `fact_superseded` | `fact_expired` | `answer_needs_review` | `attested` | `disputed` | `gap_acknowledged` | `compliance_class_set` | `evidence_added` | `job_failed` | `answer_promoted` | `tender_submitted` | `outcome_set` | `supersession_reversed`), `actor`, `payload` (JSON). `tender_submitted` is written by submit, `outcome_set` by a tender PATCH that changes the outcome, and `supersession_reversed` on a document whose exclusion is lifted (keep-both after an automatic supersession, a changed or removed decision, a date change that flips direction, or a re-evaluation).
- `comments`: `question_id`, `author`, `text`.
- `jobs`: `kind` (`ingest_document` | `extract_questions` | `triage_tender` | `draft_all`), `status` (`queued` | `running` | `done` | `failed`), `attempts`, `total`, `done`, `payload` (JSON, backend-internal and never returned: `{document_id, actor}` for `ingest_document`, `{tender_id, document_id, actor}` for `extract_questions`, `{tender_id, actor}` for `triage_tender`, `{tender_id, include_new, actor}` for `draft_all`), `results` (JSON: per-item outcomes, shape per kind under the API surface), `next_job_id` (nullable), `error`, `started_at`, `finished_at`.

Three invariants are enforced in code, each in exactly one place: a question's `status` is written only by the transition function in `review/`; a question has at most one current answer; `support_summary` is recomputed, and `needs_review` cleared when it may be, by one function whenever any segment's status changes or a new answer version becomes current; `needs_review` is set true only by dispute, fact invalidation and the ingestion step 9 removal path.

## Ingestion pipeline

Triggered on document upload as an `ingest_document` job. `ingest_status` is updated at each stage and the job reports progress, so the library and any open thread can show indexing state. Stage to step: `parsing` is step 1, `classifying` step 2, `extracting` steps 3 and 4, `embedding` step 5, `linking` steps 6 to 8, then `ready`; a status is written when its stage starts, and `jobs.total` is the number of stages the document runs, 5 for a library document and 1 for a parse-only tender document. For a tender document that is not a question pack, only step 1 runs and `ingest_status` goes straight to `ready`.

1. Parse with Docling. Persist every section to `document_sections` at the granularity defined in the data model. The file itself is stored for download; everything downstream reads from sections, never from the file.
2. Classify the document with one LLM call over the first sections and a sample of later ones; `ingest_status` is `classifying` meanwhile. Output schema: `doc_type`, `doc_kind` (for reference documents), `effective_date` (from content; null if absent), `buyer` and `submission_date` (for past submissions). Persist. If `effective_date` is null, set it to the upload time and record `effective_date_source = upload_time`. A proposal exists, and the interface shows the confirmation prompt, when `doc_type` is non-null and `classification_confirmed` is false. Confirmation or override sets `classification_confirmed`; an override of the date records `effective_date_source = user`. The pipeline does not wait for confirmation, but supersession (steps 7 and 8) is evaluated only once both documents involved are confirmed.
3. For past submissions: extract question-answer pairs by anchors. One LLM call per window of consecutive sections in document order, sized by `pair_extraction_window_tokens` in `config.py` (start at about 6,000) with one section of overlap, each section labelled with its id in the prompt. The prompt describes the three common layouts (question and answer in adjacent table cells; question as heading with answer beneath; numbered form with boxed answer cell) and asks, per pair, in document order: the question's section id and the answer's section id (the same id in the adjacent-cells layout), the first and last four to eight words of each, the copied text of each, `topics` (from the organisation's taxonomy) and `facts` (dated or expiring claims stated in the answer, each as `{fact_kind, fact_key, statement, value, effective_date, expires_on}`: `statement` is one sentence copied from the section so `find_span` can locate it; `value` holds the number, status or name; the dates are those the text states, null when it states none, and `expires_on` is never inferred). The server locates the anchors in the named sections after normalisation (see conventions) and slices the text out; the model never retypes an answer into storage. If a start anchor matches more than once, take the first match after the end of the previous pair in that section; if an end anchor matches more than once, take the nearest after the chosen start. If the normalised slice's length differs from the normalised copied text's length by more than a quarter of the latter, the anchor is treated as not located. A pair's answer lies within one section; if the end anchor is not in the named answer section, for example because the answer continues under a sub-heading, the anchor is not located and the pair follows the `find_span` path. When an anchor is not located, call `find_span` with the copied text: if found, slice at the returned offsets and `text_verified` is true; if not, store the copied text with `text_verified = false`. Pairs returned twice because of the window overlap are collapsed when their answer anchors resolve to the same offsets. Fragments that cannot be paired are written to `unpaired_fragments`. Both `text_verified = false` items and fragments appear in the document's unpaired queue for a person to fix; unverified items are never retrieved or cited until then.
4. For reference documents: chunk by section into contiguous slices with a target of roughly 400 tokens. The stored `answer_text` is the raw slice `section.text[answer_start:answer_end]`, so `text_verified` is true by construction and no check is run. Heading-path context is prepended only to the string passed to `embed()`; it is never stored. Per chunk, emit `topics` and `facts` in the step 3 shape.
5. Embed: `question_embedding` from question text (pairs only) and `answer_embedding` from answer text (pairs) or from the heading-path-prefixed chunk text (chunks). `search_tsv` is a generated column and needs no step. This step runs before deduplication, which needs the embeddings.
6. Deduplication: for each new `qa_pair`, compare its answer embedding against existing canonical items in the same organisation. Above a cosine threshold of 0.90 it joins that cluster; otherwise it becomes a new canonical item. The canonical of a cluster is re-elected on every addition or removal: a promoted answer beats an extracted pair, then the newest effective date wins. Retrieval searches all eligible items and collapses to one per cluster after fusion, so the best variant surfaces rather than the first uploaded.
7. Facts: persist each fact with its source section and `knowledge_item_id`; a null `effective_date` is filled from the document's `effective_date`, so a fact's date is either stated in its text or inherited. A fact supersedes another only when `fact_kind` and `fact_key` match, both source documents have the same `doc_type`, both are `classification_confirmed`, neither has `effective_date_source = upload_time`, and the facts' effective dates differ; the later-dated fact supersedes regardless of upload order. This fact gate applies to past submissions and reference documents alike, whatever the `doc_kind`, and fact pairs never write `supersession_decisions` rows. Facts from documents of different `doc_type`s never supersede each other; draft step 5 chooses between them. Superseding a fact calls the fact-invalidation function (traceability section) for the older fact with reason `superseded` and writes a `fact_superseded` event. When the gate is not met both facts stay current and the pair is re-evaluated when confirmation or a PATCH re-runs this step (step 9).
8. Document supersession applies only to kinds in `supersedable_doc_kinds` (all document kinds except `product_description` and `other`). When this document is `classification_confirmed` and another non-superseded, confirmed reference document of the same kind exists, write or update the pair's `supersession_decisions` row and evaluate it; no row exists while either member is unconfirmed, and until then the outstanding confirmation prompt is the only pending item. On evaluation: if the kind is in `keyed_doc_kinds` (kinds whose facts carry a `fact_key`; `dspt_confirmation` and `clinical_safety_case` to start), automatic supersession never fires, because more than one document of the kind can be current at once: `decision = pending`, `reason = keyed_kind`, and the library shows the pair; step 7 still supersedes facts between them by kind and key. Otherwise, if neither document has `effective_date_source = upload_time` and the dates differ, `decision = superseded` with `reason = auto`: the older document is retained, its `superseded_by` set, its knowledge items set `excluded_from_retrieval = true`, every current fact of it that step 7 did not already supersede passed to the fact-invalidation function with reason `superseded`, and a `document_superseded` event recorded. Otherwise `decision = pending` with `reason` `pending_date` or `tie`, and the library shows it for the user to resolve. Re-evaluation never overturns a `keep_both` or a human `superseded` unless one document's `effective_date` changed after `decided_at`.
9. Corrections: every stage is idempotent on (document, stage). A stage re-run first deletes this document's outputs of that stage and later ones (knowledge items and their facts, fragments, fact supersessions those facts set, and `supersession_decisions` rows the document is party to), re-elects the canonical of any cluster that lost a member, then re-runs. Sections are never deleted. `PATCH /documents/{id}` applies the override, sets `classification_confirmed`, then: a `doc_type` change sets `ingest_status = extracting` and enqueues `ingest_document`, so the worker's single resume rule applies; a `doc_kind` or `effective_date` change, and `POST /documents/{id}/confirm`, re-evaluate the rules of steps 7 and 8 synchronously in the request for the document's kind and, on a kind change, for the former kind, including reversing an earlier exclusion. That re-evaluation deletes and re-extracts nothing: existing `facts` rows keep their ids and have `superseded_by` recomputed (a newly superseded fact goes through fact invalidation; a pointer the rule no longer supports is cleared, which restores no segment), and the `supersession_decisions` rows the document is party to are re-evaluated. The delete-then-re-run rule applies only to the `ingest_document` job. Answer segments whose cited item was deleted by a re-run are passed to the fact-invalidation function with reason `removed`.

## Question pack ingestion and coverage triage

Triggered when a tender document with `tender_doc_kind = question_pack` is uploaded. In the hackathon a tender holds one question pack; a second upload of that kind returns 409. `questions.document_id` is what a later replace-or-append feature keys on. The upload returns the `extract_questions` job; that job enqueues `triage_tender` as its final step, writes the new id to its own `next_job_id` and to `tenders.triage_job_id`. Other tender documents run the parse-only ingest and are viewable in the source pane.

1. Parse with Docling and persist sections as in ingestion step 1. Extract questions with one LLM call per prose section, or per batch of about twenty-five consecutive row sections for tabular packs. Output per question: `section`, `number`, `text`, `word_limit`, `weighting`, `response_type`, `mandatory`, `order_index` and `topics` (one to three from the taxonomy). Topics are assigned here, once, so no later step needs a classification call. Create one `questions` row per extracted question with `status = not_started` and `coverage = unknown`, and one thread per question. Embed all question texts in one batched call and store each on `questions.embedding`. The pack's `ingest_status` is `parsing` during parsing, `extracting` while questions are extracted and embedded, then `ready`.
2. Triage every question in parallel with a concurrency limit. Per question: run retrieval (steps 2 to 4 of the draft pipeline) without synthesis, using the stored embedding. Let `best_vec` be the highest vector score (as computed in draft step 3) among the fused top eight. If `best_vec` is below `coverage_floor`, the question is `new` and no LLM call is made. Otherwise one small LLM judgement over the question and the top three candidates returns `covered` (no material gap), `partial` (gaps listed) or `new` (no candidate addresses the substance of the question). The floor is a cost gate that skips the call for obvious misses; it is not the only route to `new`.
3. Persist `coverage` and `coverage_detail`, including `best_vec` and `label_source`, so the harness can tune the floor and count how often the judgement returns `new` above it. The job reports done over total so the board fills in as it goes. Target: about a minute for a forty-question pack. Nothing in this step calls a local model.
4. Re-triage is available per tender after later library uploads. It recomputes coverage for questions still at `not_started` only.

## Draft pipeline (single question)

Inputs: question id (or free text for the tender-level thread), optional conversation history, optional user instruction. The query vector is the stored `questions.embedding` when the query is the question text itself; a rewritten turn or free text is embedded at call time and not stored.

1. Query rewrite: only when there is conversation history, rewrite the latest turn into a standalone retrieval question. This is contextualisation, not expansion. Skip when there is no history.
2. Lexical list. `search_tsv` is a stored generated column, `setweight(to_tsvector('english', coalesce(question_text, '')), 'A') || setweight(to_tsvector('english', answer_text), 'B')`, with a GIN index. Build the query in Python: lowercase the question text, split on non-alphanumerics, drop tokens in `LEXICAL_STOPWORDS`, join the rest with ` or ` and pass to `websearch_to_tsquery('english', :q)`; an empty tsquery yields an empty list. AND semantics over a long question returns nothing; OR is what lets exact identifiers such as DCB0129 or ISO 27001 score. Rank with `ts_rank_cd(search_tsv, query, 1)`, which normalises by document length so long boilerplate answers do not win on term count; the absolute scale does not matter because fusion uses rank positions only. Twenty candidates from eligible items.
3. Vector list: one list, not two. Score each eligible item as the greater of its question-embedding and answer-embedding cosine similarity to the query vector, so chunks (which have no question embedding) compete on equal terms. Twenty candidates.
4. Topic list: eligible items whose `topics` intersect the question's topics, ranked by the step 3 score. Twenty candidates. When the input is free text there are no question topics: the topic list is skipped and the other two are fused. Fuse the lists with reciprocal rank fusion (k = 60), collapse to one item per cluster keeping the member with the highest fused score (an item with no `canonical_id` is its own cluster), and keep the top eight. No reranker.
5. Facts: facts attached to the eight items, plus, for each `fact_kind` mapped to the question's topics, the single most current fact per (`fact_kind`, `fact_key`). Among current facts with the same kind and key, prefer one from a `reference` document over one from a `past_submission`, then the newest `effective_date`, ranking every fact whose date was inherited from a document with `effective_date_source = upload_time` below the rest. Facts passed over are not sent to the prompt. For free text, only the facts attached to the retrieved items.
6. Verbatim option: if the top candidate is a pair whose question-to-question cosine similarity is 0.92 or above, offer its answer as a verbatim alternative. Only the item id is persisted, as `verbatim_offer_item_id` on the version or message the draft produced; the segments are built on read by running the authoritative splitter over the item's answer text, each segment sourced to the item's section and offsets, and returned as `verbatim: {source_item_id, segments}` on answers and messages and as the `verbatim` stream event.
7. Synthesis: one Claude call with the question, its constraints (word limit, buyer name, response type), the candidates with identifiers and their own text (for a pair, the question and the answer slice; for a chunk, the slice with its heading path; never the whole section), the facts with identifiers and dates, and any history. The prompt is a constrained composition task, not "pick the best answer". The model does not return prose; it returns segments, one per sentence, each carrying the sentence text, the 0-based paragraph it belongs to, and the source identifiers and quoted source spans it rests on. Where a past answer and a current fact conflict, the fact wins and the conflict is noted. The output ends with a `gaps` list naming what the question asks for that no candidate or fact covers, and a `fact_checklist` naming the facts used. A segment with no sources is permitted only for connective sentences and must be labelled `connective`; any substantive sentence without a source is a prompt failure and is rendered as unsupported. Segments are emitted one JSON object per line so each is schema-validated as it arrives. `response_type` selects the prompt template: `yes_no` produces a one-sentence answer plus supporting sentences, `attachment` produces sentences that name the evidence to attach, `table` is drafted as sentences and flagged for manual formatting, `pricing` is never drafted, and `free_text` and `other` use the default template.
8. Segmentation: one deterministic sentence splitter, with an abbreviation list and list-item handling, is authoritative. Conformance runs on the stream, not after it: each validated model segment is passed through the splitter before a `segment` event is emitted. A model segment spanning two splitter sentences is emitted as two segments, each carrying the sources; a model segment that does not end at a sentence boundary (the splitter's boundary rule does not fire at its last character, or it ends with a listed abbreviation or an incomplete list item) is held and prepended, with a single space, to the next model segment's text before that is split, and any held remainder is flushed when the model output ends; if the next segment's `paragraph` is greater, the fragment is flushed as its own segment first. A segment formed from more than one model segment carries the union of their sources in order, the `paragraph` of the first, and `kind = substantive` if any contributor is substantive. The `index` on a `segment` event is therefore the persisted index, and it is the only index space: `support` events, attest and dispute all use it. The verbatim alternative is conformed the same way. The same splitter runs when a human edit is saved.
9. Support verification: for each sourced segment, call `find_span(quote, item_slice)` against the cited item's own slice of its section (between `answer_start` and `answer_end`; for a fact, its statement against its source section). If found, record `locator.start` and `locator.end` in section coordinates and replace `quote` with the section text at those offsets, so the popover and the pane show what the document says; a span found in the section but outside the item's slice does not count. Then one entailment call batched across all located segments decides whether each span supports its sentence. Assign `support_status`. Segments whose span was not found are `unsupported` and keep the candidate source with null offsets. Facts named in the checklist get `status` from the same check and from their `superseded_by` and `expires_on`. The word limit is checked and reported; the draft is not truncated. This step exists so that the trace shown to the user is a verified trace, not the model's claim about its own sources.
10. Persist as a new `answers` version with `author_type = ai`, recording `model` and `prompt_version`, when invoked from a card; or as a message, recording the same `model` and `prompt_version`, when invoked from a thread. `answers.text` and `messages.content` are derived from segments: sentences joined with a single space within a paragraph and a blank line between paragraphs. When invoked from a card, the new version becomes current and the transition function moves status to `ai_draft`, under the displacement rule in the review section. Generation runs to completion on the server regardless of client disconnect (see architecture). On the wire, segments arrive with `support_status = pending` and are updated once verification completes. `pending` is never stored.

Draft-all, if built, runs the pipeline for every question at `not_started` with coverage `covered` or `partial`, in parallel with a concurrency limit, as a `draft_all` job, and sets each to `ai_draft`. An option includes `new` questions, which mostly produce gap lists. The harness always drafts every question.

Query expansion beyond the rewrite step is deliberately excluded. The corpus for an early customer is one to four submissions, perhaps one to three hundred items, and fused hybrid search with the topic list should reach the same recall without the latency and noise. This is a hypothesis. The hackathon harness does not toggle expansion; recall at eight against the ground-truth mapping is the number that decides whether expansion is worth adding as a toggle later.

## Traceability

Every sentence in a response, whether it stands alone or sits inside a longer answer, must be traceable to the source material it came from, and the reviewer must be able to see that source without leaving the sentence. This is the mechanism by which the product earns trust; if it is weak, reviewers will re-read every source and the product saves nothing.

The trace has two links and both are verified. The first link, from the uploaded document to the knowledge item, is verified at ingestion: item text is sliced from a stored section, or matched against it, and `text_verified` records the result. The second link, from the knowledge item to the sentence, is verified at draft time by support verification, which matches the quoted span within the cited item's own slice, so the attribution to `source_id` is itself verified. A trace that only verified the second link would prove that a sentence rests on the library's copy of an answer, not that the copy is what the document says.

Segment record. The unit of traceability is the sentence. An answer's `segments` field is a list of:

```
{
  "index": 0,
  "paragraph": 0,
  "text": "…one sentence…",
  "kind": "substantive" | "connective",
  "sources": [
    {
      "source_type": "knowledge_item" | "fact",
      "source_id": "…",
      "quote": "the exact span in the source that supports this sentence",
      "locator": { "document_id": "…", "section_id": "…", "start": 812, "end": 941,
                   "page": 12, "table": 2, "cell_ref": "Sheet1!5", "heading_path": ["4", "4.2"] },
      "document_title": "…", "doc_type": "reference", "doc_kind": "iso_27001",
      "effective_date": "2025-03-01"
    },
    {
      "source_type": "human_attestation",
      "attested_by": "…", "note": "…", "at": "2026-09-28T10:12:00Z"
    }
  ],
  "dispute": null | { "disputed_by": "…", "note": "…", "at": "…" },
  "support_status": "supported" | "weak" | "unsupported" | "human_authored" | "connective"
}
```

Everything the hover popover shows (excerpt, document title, location, effective date, document type and kind) is read from the segment's source record; hover never triggers a request.

Rules:

- A substantive sentence with no verified source is `unsupported`. It is never hidden, softened or blended into supported text; it is rendered distinctly so the reviewer's attention goes there first.
- `weak` means the quoted span exists in the source but the entailment check was not confident, or the sentence rests on a fact that is no longer current (superseded, expired, or from a superseded document), or its cited item was removed by a re-run. It is treated like `unsupported` for review purposes but shows the candidate source.
- `human_authored` means a person wrote or substantially rewrote the sentence. That is legitimate; it is attributed to the author and timestamp rather than to a document, and it is visibly different from AI text with a document source.
- `human_attestation` is a source a reviewer can add to an `unsupported`, `weak` or `human_authored` sentence, recording "I confirm this is true" with their name and an optional note. It upgrades the sentence to `supported` with a human source and clears any dispute on it. An attestation does not survive a text change to its sentence; the sentence must be re-attested. This is how subject-matter verification is captured at sentence level rather than only at answer level.
- Dispute: a reviewer can mark a `supported` sentence as disputed with a required note. It becomes `unsupported`, keeps its existing sources for context, carries the dispute on the segment, sets `needs_review = true` and records an event. This is the downgrade path; the harness's "supported sentences a human disagreed with" metric reads from it.
- Attest and dispute modify the addressed segment of the current answer version in place; they never create a version and are refused on a non-current version. `support_summary` and `needs_review` are recomputed by the single function named under the data model.
- Fact invalidation: one function in `review/` takes a source (a fact id or a knowledge item id) and a reason (`superseded` | `expired` | `removed`). For every current answer whose segments cite that source, it sets those segments to `weak`, for a fact sets the matching `fact_checklist` entry's `status` to the reason, sets the question's `needs_review = true`, runs the recompute function, and writes one `answer_needs_review` event per affected question. It never writes `status`. It is idempotent: segments already `weak` for that source are left alone and no event is written where nothing changed. Older versions and thread messages are left as historical record. It is called from ingestion step 7 (a fact superseded by a successor), from step 8 and the supersession-decisions endpoint (every remaining current fact of a superseded document), from step 9 (items deleted by a re-run) and from the expiry sweep. The sweep runs on the worker when idle, at most once an hour, and synchronously before a submission export: facts with `expires_on` in the past and `expired_at` null get `expired_at` set, a `fact_expired` event, and the invalidation; a second run over the same facts is a no-op.
- `needs_review` is owned by the recompute function. Each time it runs on a question's current answer it sets `needs_review = false` if no substantive segment is `weak` or `unsupported`, and otherwise leaves the flag as it is. Nothing else clears it: not a status change, not `PATCH /questions/{id}`, not re-saving unchanged text. It is set true only by dispute, fact invalidation and the step 9 removal path; a fresh draft, an accepted verbatim or a human edit never raises it, since their `unsupported` and `weak` sentences are caught by the `sme_verified` gate. Support verification never returns a segment to `supported` while its fact source is not current; only a human attestation, or a rewrite that cites a current source, restores it. Status does not change by itself, but `sme_verified` and submission export refuse while `needs_review` is true.
- Support score: `support_summary` yields one number per answer, the share of substantive sentences that are `supported`, shown as a decimal such as 0.91. It measures how much of the answer rests on verified evidence, not the probability that the answer is correct, and the interface must label it as evidence coverage. This is the per-requirement confidence figure the pitch shows.

Editing behaviour. When a person edits an answer, the server re-splits the saved text with the authoritative splitter, assigning `paragraph` from blank lines, and re-aligns segments. Procedure: take the base version's stored segment texts as the old sentence list (they are already splitter output; never re-split them), split the saved text with the authoritative splitter, normalise both lists with the shared normaliser, and run a sequence diff over the two lists (`difflib.SequenceMatcher`). Sentences in equal blocks keep their segments verbatim. Inside a replaced block, pair old and new sentences by `SequenceMatcher(None, old, new).ratio()` on the normalised text (a string ratio, not embedding cosine), highest pair first, each sentence used once, accepting pairs at or above `realign_min` (0.85). Paired sentences keep their document and fact sources and drop to `weak`; a `human_attestation` source is dropped, and so is any `dispute`: neither survives a text change to its sentence, and the rewrite is the response to a dispute, with the `disputed` event and the base version as the record. Unpaired new sentences are `human_authored`; unpaired old sentences are dropped. Then one entailment call batched over the sentences that became `weak` by edit restores `supported` where it passes; if no sentence falls in that band, no LLM call is made. Inserting "not" or changing a year must not carry a `supported` status, which is why paired sentences are re-verified rather than trusted. Sources are never silently carried onto text they did not support. A human-edit version copies `gaps` and `fact_checklist` from its base version, so acknowledgements survive editing.

Interface requirements (Roger designs the visuals; these are the behaviours):

- Inline, not in a footnote list. Each sentence carries an unobtrusive marker at its end. Support status is conveyed by the marker and by a text-decoration style, never by colour alone. A segment with a `dispute` is rendered as `unsupported` and shows the dispute note.
- Hover on a sentence (or focus, by keyboard) shows a popover with the source excerpt, the document title, the location (page, table, row, section), the document's effective date, and the document type and kind. No click is required to see this.
- Click on the marker, or a "verify source" control on a selected sentence, opens the source document in a side pane at the stored section, scrolled to the offsets, with the quoted span highlighted. The answer editor remains visible. The pane never re-parses the file and never searches for text; it reads `document_sections` and the locator offsets, renders `text` as stored, pre-formatted, and never reflows a table row into an HTML table, so the offsets hold. If a source has null offsets, the pane opens the section without a highlight and shows the quote beside a "span not located in this section" notice. `human_attestation` sources have no locator and do not open the pane.
- A support summary sits at the top of the answer: for example "14 of 16 sentences supported, 2 need review", with the support score beside it. Clicking it, or pressing a single keyboard shortcut, jumps to the next `unsupported` or `weak` sentence. Reviewers should be able to move through only the sentences that need attention.
- Saving an edit shows a saving state until the new version returns and replaces the editor contents.
- The board and table views show the support summary and score per question so the bid lead can see which answers carry unreviewed claims without opening them.
- Chat messages render the same way as answers; a message is a list of segments with the same behaviours.

Export. The submission export contains clean prose. Submission mode writes every question in `order_index` with its section, number and text. A question whose status is `approved` gets its current answer text; any other question, including pricing questions without an approved version, gets the single placeholder line `[No approved answer]`. Submission mode runs the expiry sweep, then refuses (409) while any question has `needs_review`. The interface warns before export using the questions-approved-over-total count the tender header shows. Review mode (if built) writes the current answer of every question that has one, regardless of status, with each sentence's sources as Word comments, and the same placeholder where no version exists.

Evaluation. The harness reports, per answer, the share of substantive sentences that are `supported`, the share of cited spans found at the `verbatim` tier and the share found only at the `near` tier, the share of extracted items with `text_verified` true, and a human spot-check of twenty sentences per run for whether the cited span actually supports the sentence. The target for the demo is that a reviewer can approve a `covered` question by reading only its unsupported sentences and the gap list.

## Chat threads

The knowledge base is scoped to the organisation, never to a thread. Any library document uploaded anywhere becomes available to every thread once indexed. Threads are scoped to a question (the common case, MVP) or to a tender (if time allows; for questions about the tender as a whole, such as which sections carry the most weight; it retrieves from the library exactly as a question thread does, and the tender's own documents are not retrievable in the hackathon). Each assistant message is stored as segments with sources and support status, exactly as answers are, together with the rewritten query, retrieved item identifiers, gaps, fact checklist and verbatim offer, so a thread reloads with everything the assistant region shows and any response is auditable sentence by sentence. Conversation history is passed to the synthesis call so instructions such as "make that shorter" or "tailor it for a Scottish health board" work; "regenerate with instruction" in the assistant region is a thread message. Mid-conversation uploads run through the ingestion pipeline as jobs; the thread displays indexing status and new material is included in retrieval as soon as it is ready with no reprocessing of existing items.

Any assistant message can be saved as an answer. This creates a new `answers` version on the thread's question with `author_type = ai`, makes it current, links the message to it, copies the message's `segments`, `gaps`, `fact_checklist`, `verbatim_offer_item_id`, `model` and `prompt_version` onto the version with `text` and `word_count` derived from the segments, and sets the question's status to `ai_draft` because an AI-authored version is now current, under the displacement rule in the review section. Without this action, approved text would live in a chat stream and the learning loop would have nothing to attach to.

## Review pipeline

Question status is ordinal and named by who has stood behind the current answer:

1. `not_started`: no answer version exists.
2. `ai_draft`: the current version was produced by the pipeline and not edited.
3. `writer_edited`: a person has edited or rewritten the current version.
4. `sme_verified`: a named subject-matter reviewer has confirmed factual accuracy (for example a clinical safety officer for clinical safety answers, an IG lead for information governance answers).
5. `approved`: the bid lead has signed off the answer for submission.

Any human edit creates a new version, re-aligns segments as described in the traceability section, and moves status to exactly `writer_edited` through the transition function whatever it was before: up from `not_started` or `ai_draft`, down from `sme_verified` or `approved`, with a `status_changed` event, because nobody has yet verified or approved the new current version. Moving to `sme_verified` requires that every substantive sentence is `supported` (by a document source or a human attestation) and that `needs_review` is false; the transition control lists the sentences blocking it, including un-attested `human_authored` ones. Moving to `approved` additionally requires an empty gap list or an acknowledgement of each remaining gap. An acknowledgement matches a gap when the two strings are equal after the shared normalisation; acknowledgements that match no gap in the current version stay in the row but are ignored by the gate and not shown, so a reworded gap must be acknowledged again. Status can move backwards (for example, an SME rejects an answer and it returns to `writer_edited`). Every transition writes an `events` row with actor and timestamp. Colours in the UI are display only and must not be encoded in data.

Transition matrix for `PATCH /questions/{id}`: the human targets are `writer_edited`, `sme_verified` and `approved`. `not_started` is set only at question extraction and `ai_draft` only by card draft, save-as-answer, accept-verbatim and draft-all; for both, `allowed_transitions` returns `allowed: false` with blocker `{kind: "system_only"}`. From `not_started` every target is blocked with `{kind: "no_answer"}`. With a current version, `writer_edited` is always allowed, forwards from `ai_draft` or backwards from `sme_verified` or `approved`. `sme_verified` is gated as above in either direction. The `approved` gate is the `sme_verified` gate plus the gap gate, and `approved` may be reached directly from `writer_edited` or `ai_draft` when both pass. A request for the current status is a no-op that writes no event.

Displacement. AI writes never displace a version a person has stood behind without an explicit confirmation. Draft-all only drafts questions at `not_started`. Card draft, save-as-answer and accept-verbatim on a question whose status is past `ai_draft` return 409 unless the request body carries `confirm_displace: true`; the interface's confirmation dialog sets that flag. With the flag, the new AI version becomes current, the displaced version stays in the version history, and status moves to `ai_draft` through the transition function. No code path other than the transition function writes `status`.

Compliance class is set by a person on any question, typically the mandatories, and is independent of status and coverage. The tender header shows the count of C and unclassified mandatory questions. A C blocks nothing in software; it is a bid decision, and the product's job is to make it impossible to miss.

Pricing questions (`response_type = pricing`) receive no AI draft, no verbatim option and no draft-all; their answer region is a human-only editor with the same versioning and status transitions.

Per question: assignee, reviewers (held in the sidecar), comments, evidence list, version history with diff between versions, and the event log.

Comments. The backend is the record for every comment. A plain comment is `POST /questions/{id}/comments`, which writes a `comments` row and a `comment_added` event. An anchored comment made in the front end, on a span of an answer version, is mirrored through the same endpoint first, so the row and the event exist, and only then does the sidecar store the anchor (segment indices and offsets into that version) and the thread structure (replies, resolved state). The sidecar holds the anchor and thread structure only and never the only copy of a comment's text; a message removed in the sidecar leaves the backend row and event in place, so the audit trail is complete whichever tab a comment was made in.

When a tender is marked `submitted`, every `approved` answer is offered for promotion into the library as a `promoted_answer` knowledge item, tagged with buyer, date and outcome when known, and passed through deduplication, where it wins canonical election. When the tender's `outcome` is set later, the tags update. This closes the learning loop. Promotion is built if time allows; the fields exist regardless.

This section specifies screens, regions and states. Visual design is Roger's.

Tender-level actions: upload tender documents, re-triage, draft all (if built), export, mark submitted, set outcome, open tender-level thread (if built), edit name, buyer and deadline, archive or restore, delete a tender that was never submitted, fill the buyer's form at confirmed locations.

Global upload: available from every screen; documents go to the organisation library regardless of where they were uploaded, unless uploaded into a tender as a tender document.

## API surface

REST, JSON, service-authenticated. When `SERVICE_SECRET` is set, every route including `/health` requires `Authorization: Bearer <secret>`, compared in constant time, and answers 401 otherwise; the only caller is the Next.js server, which holds the secret. There is no user authentication in the API. `org_id` is taken from the `X-Org-Id` header, which the proxy sets from the business's mapping, and defaults to the seeded organisation when absent (tests and the harness). The acting user's display name is sent on every mutating request as an `X-Actor` header, set by the proxy from the member's profile; a mutating request without it is rejected with 400 so a missing actor is caught early rather than written blank into the audit trail. The server stamps it into `events.actor`, `answers.author_name` (human versions only), `attested_by`, `disputed_by`, `acknowledged_by` and `comments.author`; request bodies never carry the actor. `assignee` is data about the question, may name anyone, and travels in the body. Events written by the worker or by pipeline rules with no request behind them carry `actor = system`; a job enqueued by a user carries the header value in its payload so events from draft-all name the person who started it. Every long-running operation returns a `job_id`, except the two streaming endpoints, which return the stream itself and report the persisted id in the `done` event. Follow-up: the display name is still the audit identity, so a rename leaves history under the old name; a stable actor identifier carried alongside `X-Actor` is the agreed next step (Puru).

System and organisations:

- `GET /health` returns `{status, llm_provider, embedding_provider, service_secret_enabled, synthetic_demo}`. It sits behind the secret like every other route; the front end reads it at boot and, in demo mode, refuses fake or synthetic providers and an unenforced secret.
- `POST /organisations` body `{id, name}` provisions an organisation with the caller-supplied id and the default taxonomy. Idempotent, so a retry across the two databases is safe; 409 when the id exists under a different name. Called by the sidecar when a business is created, never from a browser.

Documents and library:

- `POST /documents` (multipart) upload to the library; returns the document and a `job_id`. `GET /documents` (library documents only, `tender_id` null) and `GET /documents/{id}` return every `documents` column plus `item_counts` by `item_type` and `fact_count`. `PATCH /documents/{id}` (body: any of `doc_type`, `doc_kind`, `effective_date`, `buyer`, `submission_date`; sets `classification_confirmed`, records `effective_date_source = user` when the date changed, runs the corrections in ingestion step 9, returns the document plus `job_id` or null). `POST /documents/{id}/confirm` (empty body; sets `classification_confirmed`, evaluates supersession, returns the document). `GET /documents/{id}/sections`. `GET /documents/{id}/file` returns the original stored file with its filename, scoped to the organisation; it exists for download and for buyer-form filling, which reads the original and writes approved answers into a copy at confirmed locations. Nothing in the pipeline reads the file after parsing.
- `GET /documents/{id}/unpaired` returns the document's `text_verified = false` items and its unresolved fragments. `POST /documents/{id}/pairs` takes either `{item_id, section_id, answer_start, answer_end, question_text?}` (fidelity fix: the server re-slices from the stored section, so `text_verified` is true by construction, then runs ingestion steps 5 and 6 for that item) or `{question_fragment_id | question_text, section_id, answer_start, answer_end}` (manual pairing: creates the item with `text_verified = true`, sets `resolved_item_id` on any fragment used, runs steps 5 and 6). Confirmation is always by pointing at a span, never a bare vouch. Either path writes a `pair_fixed` event.
- `GET /sections/{id}?start=&end=` returns the section row (`id`, `document_id`, `order_index`, `heading_path`, `page_start`, `page_end`, `table_index`, `cell_ref`, `text`), `document` (`id`, `filename`, `doc_type`, `doc_kind`, `tender_doc_kind`, `effective_date`, `superseded_by`) and `highlight: {start, end} | null` (null when absent or out of range).
- `GET /library/items` (flat list with `text_verified`, `item_type`, source document), `GET /library/items/{id}` (with variants and locator), `GET /library/facts`. `GET /library/supersession-decisions` (pending rows with both documents' filename, `doc_kind`, `effective_date` and `effective_date_source`). `POST /library/supersession-decisions/{id}` body `{decision: "superseded", superseding_document_id}` or `{decision: "keep_both"}`; `superseded` applies the step 8 effects to the other document; both write a `supersession_decided` event.

Tenders and jobs:

- `POST /tenders`, `GET /tenders`, `GET /tenders/{id}`, `PATCH /tenders/{id}` (name, buyer, deadline, outcome, outcome notes, regime, framework flag; `status: archived` archives and `status: open` restores, a submitted tender restoring to `submitted`; an outcome change writes `outcome_set`). `DELETE /tenders/{id}` deletes a tender that was never submitted, with its documents, questions, answers, threads and their events; 409 once submitted, since its approved answers may be in the library (archive instead), and 409 while a job for the tender or for one of its documents (including a parse-only ingest), a draft, or a streaming reply on one of its threads is running. `POST /tenders/{id}/documents` (multipart with `tender_doc_kind`; always returns the document and a `job_id`: for a question pack the `extract_questions` job, otherwise the parse-only ingest; 409 for a second question pack). `POST /tenders/{id}/retriage` (returns a `triage_tender` job). `POST /tenders/{id}/draft-all` (returns a job; if built). `POST /tenders/{id}/submit` (409 once `submitted_at` is set, even after archiving, so a submission is recorded once; 409 for an archived tender that was never submitted, which must be restored first; submit never restores). Both upload routes return 413 with a message naming the limit when a file exceeds `max_upload_bytes`, before any row or file is written. `GET /tenders/{id}/export?format=docx|xlsx&mode=submission|review` (rules under Traceability, Export; xlsx and review mode if built).
- `GET /jobs/{id}` returns `{id, kind, status, attempts, done, total, error, started_at, finished_at, next_job_id, results}`. `total` and `results` per kind: `ingest_document`, `total` is the number of stages and `results` is empty, clients read the stage from `ingest_status`; `extract_questions`, `total` is the number of sections or row batches, `results` is `[{item_id: section_id, outcome: "extracted" | "failed", detail: questions created}]`; `triage_tender`, `total` is the number of questions, `results` is `[{item_id: question_id, outcome: coverage}]`, and coverage is also persisted so the board may refetch questions on each poll instead; `draft_all`, `total` is the number of eligible questions, `results` is `[{item_id: question_id, outcome: "drafted" | "skipped" | "failed", detail: answer id or error}]`.

Response shapes for lists: `GET /tenders` returns `[{id, name, buyer, deadline, days_remaining, status, outcome, questions_total, questions_approved, words_total, words_approved}]`, where `words_total` is the sum of `word_limit` over questions that have one and `words_approved` is the sum of `word_count` of current answers on `approved` questions. `GET /tenders/{id}` returns the tender row plus those aggregates, `c_count`, `unclassified_mandatory_count`, `needs_review_count`, `extract_job_id`, `triage_job_id` and `documents` (each with `tender_doc_kind` and `ingest_status`). `GET /tenders/{id}/questions` returns every question row with an embedded `current_answer: {id, version, author_type, author_name, word_count, support_summary, updated_at} | null` (no `segments`) and `thread_id`.

Questions and answers:

- `GET /questions/{id}` returns the question row plus `thread_id`, `evidence` (`[{document_id, filename, note}]`), `comments`, `current_answer` in full (`segments`, `gaps`, `fact_checklist`, `verbatim`), `draft_in_progress` (from the in-process registry) and `allowed_transitions: [{to, allowed, blockers}]` for every status, computed by the transition function so the client never re-implements the gates; `blockers` is `[{kind: "segment" | "gap" | "needs_review" | "no_answer" | "system_only", index?, gap?}]` (matrix under the review pipeline).
- `PATCH /questions/{id}` (assignee, status, compliance class, compliant-by). A `status` that is not allowed returns 409 with `{blockers}` in the same shape; the other fields are never gated.
- `POST /questions/{id}/evidence` body `{document_id, note?}` (writes an `evidence_added` event); `DELETE /questions/{id}/evidence/{document_id}`.
- `POST /questions/{id}/draft` (stream) body `{instruction?, confirm_displace?}`; card invocation; 409 on a question past `ai_draft` without the flag, 409 while a draft is already running, never for `response_type = pricing`.
- `GET /questions/{id}/answers` (each with `segments`). `POST /questions/{id}/answers` (human edit; body `{text, base_version_id}`; synchronous, runs the re-split, re-alignment and one batched entailment call, may take a few seconds; returns `{answer, question}` with final statuses and the question at `writer_edited` whatever it was before; if `base_version_id` is not the current version, 409 with `{current_answer}` and nothing written).
- `POST /questions/{id}/verbatim` body `{source_item_id, confirm_displace?}` creates a new `ai` version from the item's verbatim segments with `verbatim_source_item_id` set and `model` and `prompt_version` null, runs support verification, makes it current, moves status to `ai_draft`; same 409 rule; writes `verbatim_accepted`.
- `POST /answers/{id}/segments/{index}/attest` body `{note?}`; permitted only on an `unsupported`, `weak` or `human_authored` segment of the current version (409 otherwise). `POST /answers/{id}/segments/{index}/dispute` body `{note}`; permitted only on a `supported` segment of the current version. Both return the full updated answer and the question row.
- `POST /questions/{id}/gaps/acknowledge` body `{gap, note}`, where `gap` must equal a string in the current answer's `gaps` after normalisation (422 otherwise); returns the question row.
- `GET /questions/{id}/events` returns `[{id, event_type, actor, payload, created_at}]` newest first. `POST /questions/{id}/comments` body `{text}` writes a `comments` row and a `comment_added` event; it is the record for every comment, including anchored comments made in the front end, which are mirrored through it before the sidecar stores their anchor.

Threads:

- `POST /threads` creates tender-level threads only (question threads are created at extraction). `GET /threads/{id}` returns `{id, tender_id, question_id, title, reply_in_progress, messages: [{id, role, content, segments, support_summary, gaps, fact_checklist, verbatim, model, prompt_version, answer_id, created_at}]}`. `POST /threads/{id}/messages` (stream) body `{content}`; 409 while a reply is already running for that thread: the user message is persisted first, the pipeline runs with the thread's history and `content` as the instruction, the reply is persisted as an assistant message and `done` carries its id. `POST /messages/{id}/save-as-answer` body `{confirm_displace?}`; same 409 rule.

Fixtures:

- `GET /fixtures/answer` returns `{question, answer, thread}` in the shapes of `GET /questions/{id}`, one item of `GET /questions/{id}/answers` and `GET /threads/{id}`. The answer has at least one segment in each support status; one segment with two sources; one `fact` source; one `human_attestation` source; one disputed segment; a non-empty `gaps` list, one gap acknowledged; a populated `fact_checklist`; and a verbatim offer. Every `locator.document_id` and `section_id` resolves: the seed inserts one fixture document (`doc_type = reference`, `doc_kind = other`, `classification_confirmed = true`, a fixed `effective_date` with `effective_date_source = user`, `ingest_status = ready`) and its `document_sections` rows under fixed UUIDs from a pre-parsed JSON file in `eval/data/fixtures/` (no parsing at seed time, no `knowledge_items`, so it never enters retrieval, sits outside `supersedable_doc_kinds`, and never shows the confirmation prompt), so `GET /sections/{id}` and the popover work against it on day one.
- `POST /fixtures/draft` replays the same answer over the streaming contract, emitting every event type in realistic order with about 150 ms between events, including one model segment that is split into two `segment` events. `POST /fixtures/draft?fail_after=3` emits three segments and then `error`. Neither persists anything.

Streaming contract. Streaming endpoints are `POST` with a JSON body. The response is `Content-Type: application/x-ndjson`, HTTP 200 sent as soon as the request is accepted; anything that fails after that arrives as an `error` event. Consumed with `fetch` and a stream reader rather than `EventSource`. Every line is one JSON object with a `type` field. Events, in emission order:

- `verbatim` (only when draft step 6 fires; before any segment): `{source_item_id, similarity, segments}`.
- `segment`: one full segment record with `support_status: "pending"`, already conformed to the splitter, so its `index` is the persisted index; each source carries `locator.document_id` and `section_id` from the cited row and `start` and `end` null until verification.
- `gaps`: `{gaps: [string]}` and `fact_checklist`: `{fact_checklist: [...]}`, as stored.
- `support`: `{index, support_status, sources}`, one per segment as verification completes; `sources` is the verified list with `start` and `end` filled where the span was found, and the client replaces that segment's sources wholesale, so click-to-source works on a streamed draft without a refetch.
- `done`: the complete persisted answer or message object, including `support_summary`, `model` and `prompt_version`, and `word_count` on an answer; the client replaces its accumulated state with it. Always the last line on success.
- `error`: `{code, message}`. Always the last line. No answer version or assistant message is persisted for a failed run and the question's status is unchanged; a thread's user message, already stored, remains.

A client that lost a question stream polls `GET /questions/{id}` for `draft_in_progress` and, when false, reloads the answers: a new current version means success, none means the run failed. A client that lost a thread stream polls `GET /threads/{id}` for `reply_in_progress` and, when false, reloads messages: a new assistant message means success, none means failure. The same contract serves questions and threads; `POST /fixtures/draft` is its reference implementation.

## Evaluation harness

Build this in the first phase, before tuning anything. Without it the project drifts into prompt tinkering.

Data: hold out one past submission entirely. Ingest the others, and confirm every synthetic document after ingest so the supersession gate behaves as it does for a user. Treat the held-out submission's questions as the incoming question pack and its answers as ground truth. The synthetic data generator writes `eval/data/ground_truth.json`, mapping each held-out question to the ingested item or items that answer it (the deliberate overlap makes this known at generation time); held-out questions with no counterpart are labelled `new`. Human labels (coverage labels, spot-checks, disputes) are stored under `eval/labels/` so they accumulate across runs instead of being redone. Each run writes `eval/reports/<timestamp>.md` with every metric and toggle table, and a `.json` twin; MVP step 6 means opening the latest `.md`. Metrics that need human labels are reported as `not labelled` when `eval/labels/` has no entries for that run, never as zero; whoever runs the harness labels the twenty spot-check sentences before a run's numbers are quoted.

Metrics:

- Extraction: pairs extracted over pairs present, checked by hand on one document; and extraction fidelity, the share of extracted items with `text_verified` true, against the target in `config.py`.
- Retrieval recall at eight: for each held-out question with a counterpart, is any member of a counterpart's cluster (the item, its canonical, or a variant) among the eight candidates synthesis receives after fusion and collapse.
- Coverage accuracy: does the triage label agree with the human label on the held-out questions; reported with how often `new` came from the floor versus the judgement.
- Draft quality: normalised edit distance between the draft and the held-out approved answer, kept as a cheap proxy; and an LLM judge score using an expert bid reviewer prompt against the held-out answer, on a five-point scale. Both are reported stratified by coverage label, and every held-out question is drafted regardless of coverage, so the `new` bucket is visible rather than hidden.
- Traceability: share of substantive sentences `supported`; share of cited spans found at the `verbatim` tier and share found only at the `near` tier; human spot-check of twenty sentences per run for whether the span supports the sentence; share of `supported` sentences a human disputed (the number that must be low for reviewers to skip re-checking).
- Latency: per-question draft time and time to a triaged board for the pack.

Toggles: topic list on or off; single vector list versus answer-embedding only; LLM rerank on or off (harness only, Phase 5). Report each as a table so the pitch can quote numbers.

Benchmark policy: hackathon numbers come from synthetic data and are labelled as such wherever they are quoted. Real past tenders join the benchmark only as design partners contribute them under agreement. No Tandem submission is ever loaded. Synthetic demo mode (`SYNTHETIC_DEMO=true`, the heuristic double in `app/llm/synthetic.py`) produces no benchmark numbers at all: it shows that the modules connect, and a run under it is reported as plumbing evidence, never as extraction, recall, coverage or draft quality. The harness's synthetic-data numbers come from real providers over synthetic documents; the two are different things and are never conflated.

## Conventions for Claude Code

- Every LLM call goes through `app/llm/` with a Pydantic output schema and validation; no free-form parsing of model output elsewhere. Streamed segments are validated one object per line.
- Prompts live as versioned files under `app/llm/prompts/`, not inline strings. Every AI answer records the `prompt_version` and `model` that produced it; verbatim and human versions record null.
- Thresholds live in `config.py` and are read by the harness: dedup 0.90; verbatim 0.92; `coverage_floor` 0.45 (highest step-3 vector score among the fused top eight; the value was set on a reranker scale before the cross-encoder was removed and must be re-based on cosine against the harness before the demo); `realign_min` 0.85 (string ratio, not embedding cosine); `span_match_min` 0.90 (string ratio); extraction fidelity target 0.90; `pair_extraction_window_tokens` 6000; `max_attempts` 3.
- Fixed lists live in `config.py`: fact kinds with topic and `key_rule`; document kinds, `supersedable_doc_kinds` and `keyed_doc_kinds`; tender document kinds; `LEXICAL_STOPWORDS`, a procurement-generic list of question boilerplate removed before the lexical query is built (`describe, detail, explain, outline, provide, confirm, please, supplier, bidder, organisation, organization, approach, ensure, requirement` to start, tuned against the harness; it must never contain sector terms); the table row and cell delimiters.
- One text normaliser and span finder, in `app/ingest/normalise.py`, is used by the fidelity check, support verification (segments and facts), gap matching, re-alignment and the harness. No other code matches text against sections. `normalise(text)` applies NFKC; maps curly quotes, en and em dashes and non-breaking spaces to ASCII equivalents; removes soft hyphens and joins a word split by a hyphenated line break; collapses whitespace to one space; lowercases; and returns an index mapping every normalised position back to the original. `find_span(quote, text)` returns `(start, end)` into the original text or none: first an exact match of the normalised quote in the normalised text (tier `verbatim`); failing that, a windowed alignment (tier `near`): slide a window of the normalised quote's length over the normalised text starting at each word boundary, keep the window with the highest `difflib.SequenceMatcher(None, quote, window, autojunk=False).ratio()`, trim its ends by whole words while the ratio improves, and if the final ratio is at least `span_match_min` map the window back through the index to original offsets (`end` exclusive); otherwise none.
- One sentence splitter, in `generate/segmentation.py`, is used for model output, the verbatim offer and human edits. No other code splits sentences.
- No reranker in the product retrieval path and no local inference models for retrieval or generation. Docling's PDF weights are baked into the image at build time.
- Tests: pytest; unit tests for fusion and collapse, thresholds, state transitions and blockers, displacement rule, canonical election, supersession gate (unconfirmed, upload-time date, tie, keyed kind, keep-both), job requeue and `max_attempts`, anchor disambiguation, `find_span` tiers; a segmentation test where one model segment is split and two are merged, asserting emitted indices equal persisted indices and that the merged segment carries both contributors' sources; a re-alignment fixture where an answer saved with unchanged text keeps every segment support status and the question moves to `writer_edited`; a fact-expiry test (a current answer citing a fact expired yesterday gets `weak` segments, an updated checklist, `needs_review` and exactly one event; a repeated sweep changes nothing); one integration test that ingests a synthetic submission and asserts recall on its own questions.
- Never use "RAG" as an identifier. Use `retrieval`, `coverage`, `status`. Never use "triage" for compliance class.
- Generated text is never stored or returned as a plain string without `segments`. Any code path that produces prose for the user goes through the segment schema and support verification. `pending` is a wire status only.
- Never render a source by opening the file. Read `document_sections` and offsets.
- British spelling in user-facing strings.
- Authentication lives in the frontend sidecar. The API stays service-authenticated by `SERVICE_SECRET` and never gains user accounts, sessions or role checks; identity reaches it only as `X-Actor` and `X-Org-Id` from the proxy. Billing and portal integrations remain out of scope, however convenient they seem.
